# Avito Recap — персональные итоги года

Веб-приложение в формате интерактивной story, которое собирает год пользователя на Авито в короткую персональную историю: активность, интересы, сценарий поведения, достижения, следующий полезный шаг и безопасную карточку для публикации.

Проект построен как полноценный клиент–серверный продукт: frontend получает данные через типизированный Proto/ConnectRPC-контракт и не дублирует backend-бизнес-логику на клиенте.

---

## Что умеет продукт

Пользователь выбирает тестовый профиль, после чего проходит персональный recap из нескольких экранов. Состав истории динамический: обязательные и опциональные карточки формируются на основании ответа backend.

Основной пользовательский путь:

```text
Выбор профиля
      ↓
Генерация итогов
      ↓
Персональная story
      ↓
Следующий полезный шаг
      ↓
Безопасный SHARE
```

В recap поддерживаются следующие типы экранов:

- `INTRO` — персональное вступление;
- `YEAR_ACTIVITY` — агрегированная активность за год;
- `TOP_CATEGORY` — главный интерес пользователя;
- `ACTIVE_MONTH` — наиболее активный месяц;
- `BEHAVIOR` — итоговый пользовательский сценарий;
- `ACHIEVEMENT` — достижения года;
- `MISSED_OPPORTUNITY` — опциональная возможность продолжить действие;
- `NEXT_ACTION` — персональный следующий шаг;
- `SHARE` — публичная безопасная карточка.

Количество экранов не зашито во frontend: интерфейс корректно работает с разным набором карточек и не зависит от количества тестовых профилей.

# Мой вклад в проект

В проекте я отвечал за **frontend, пользовательский опыт и визуальную подачу итогов года**. Backend и расчёт бизнес-правил не входили в мою зону ответственности: клиент использует уже сформированные backend-данные и отображает их через типизированный контракт.

## 1. Спроектировал пользовательский сценарий

Я ушёл от формата обычного dashboard и построил recap как полноэкранную интерактивную историю.

Реализованы:

- последовательное прохождение карточек;
- progress indicator;
- переходы вперёд и назад;
- swipe/drag-навигация;
- управление с клавиатуры;
- автоматический cinematic-режим;
- сохранение прогресса просмотра;
- возможность продолжить историю после перезагрузки;
- отдельная кнопка возврата к списку профилей, чтобы навигация не зависела от логотипа.

Главная идея интерфейса — не просто показать статистику, а превратить агрегированные данные пользователя в короткую эмоциональную историю.

## 2. Разработал визуальную систему recap

Для разных типов карточек сделаны разные композиции, чтобы история не ощущалась набором одинаковых экранов.

В frontend появились:

- индивидуальная композиция для каждого типа карточки;
- динамические фоновые мотивы;
- мягкие градиенты и Avito-inspired акценты;
- разные переходы между типами сцен;
- визуальный символ/тотем года;
- анимированные числовые метрики;
- отдельные визуальные представления категорий, поведения, достижений и CTA;
- интерактивные эффекты на desktop без зависимости от WebGL.

При этом декоративная часть отделена от данных: frontend не должен придумывать пользовательские факты, которых нет в контракте.

## 3. Переработал отображение бизнес-данных

Во время разработки я отдельно пересмотрел границу между backend-бизнес-логикой и frontend-представлением.

Из пользовательского интерфейса были убраны технические и плохо объяснимые детали вроде:

- внутренних порогов;
- `score`;
- evidence-правил;
- формулировок вида «порог ≥ 3»;
- объяснений вида «почему рекомендуем это»;
- frontend-придуманных характеристик пользователя, которые не являются частью утверждённой продуктовой логики.

Frontend показывает пользователю итог, который пришёл из продуктового контракта, а не раскрывает внутреннюю механику вычисления правил.

## 4. Провёл большую работу по responsive UI

Одна из основных частей моей работы — адаптация интерфейса под реальные размеры экранов, а не только под desktop-макет.

Я исправил проблемы, при которых элементы:

- выходили за пределы viewport;
- перекрывали друг друга;
- растягивались на всю высоту экрана;
- создавали ненужный page scroll;
- становились нечитаемыми на узких или низких экранах.

Отдельно были переработаны:

- страница выбора профилей;
- `INTRO`;
- `YEAR_ACTIVITY`;
- `TOP_CATEGORY`;
- `ACTIVE_MONTH`;
- `BEHAVIOR`;
- `ACHIEVEMENT`;
- `MISSED_OPPORTUNITY`;
- `NEXT_ACTION`;
- `SHARE`;
- экраны генерации и demo action.

Например, карточки достижений больше не растягиваются до высоты всей story: их размер определяется контентом, а сетка перестраивается в зависимости от ширины экрана.

На странице профилей длинный список не должен сдвигать главный hero-блок вниз: список имеет собственное поведение прокрутки, а основной контент остаётся в ожидаемой позиции.

## 5. Сделал frontend независимым от количества профилей

Список профилей строится динамически из ответа API. Layout не должен предполагать фиксированное число пользователей.

Это важно для реального продукта: тестовых сценариев может быть несколько, а реальных пользователей — сколько угодно. UI должен масштабироваться без изменений в компонентах.

## 6. Реализовал безопасный SHARE flow

Для публичной карточки используется отдельный минимальный набор данных.

Frontend не переносит в публичный SHARE:

- имя пользователя;
- аватар;
- внутренний recap ID;
- точные числовые метрики;
- score/evidence;
- причины назначения сценария;
- информацию о черновиках и диалогах;
- внутренние object IDs.

Публичная карточка строится только из разрешённого share payload.

Также реализован редактор SHARE с несколькими композициями и форматами экспорта.

## 7. Добавил собственную звуковую систему

Для recap реализован `SonicEngine` на Web Audio API.

Звук используется как дополнительный слой интерфейса:

- переход между карточками;
- появление метрик;
- reveal поведения;
- достижение;
- CTA;
- финал истории.

Для разных сценариев поведения предусмотрены разные звуковые профили. При этом звук **выключен по умолчанию** и полностью опционален.

## 8. Добавил accessibility и progressive enhancement

В интерфейсе учтены:

- `prefers-reduced-motion`;
- управление с клавиатуры;
- `aria-label` для интерактивных элементов;
- live announcement текущего экрана;
- отключаемый звук;
- haptic feedback только на поддерживаемых устройствах;
- fallback-поведение для декоративных эффектов.

Анимации не являются обязательными для использования продукта.

## 9. Интегрировал frontend с типизированным API-контрактом

Frontend работает с backend через **Proto + ConnectRPC**.

Основной поток данных:

```text
Go backend
    ↓
Proto contract
    ↓
ConnectRPC
    ↓
Generated TypeScript schemas
    ↓
proto-mapper
    ↓
Frontend domain model
    ↓
React UI
```

За счёт этого компоненты не работают напрямую с сырым transport-ответом и остаются отделены от сетевого слоя.

# Frontend-архитектура

Frontend построен на React + TypeScript и разделён по ответственности.

```text
frontend/src/
├── app/                  # роутинг и провайдеры приложения
├── entities/
│   └── recap/            # доменная модель recap, mapper и UI карточек
├── features/             # пользовательские действия
├── pages/                # страницы приложения
├── shared/
│   ├── api/              # ConnectRPC transport/API layer
│   ├── lib/              # общие frontend utilities
│   ├── sound/            # SonicEngine и звуковые профили
│   └── ui/               # переиспользуемые UI-компоненты
├── widgets/
│   └── recap-player/     # story player и связанные сценарии
└── test/                 # frontend-тесты
```

Такое разделение позволяет независимо развивать transport, доменную модель, визуальное представление и пользовательские сценарии.

# Запуск проекта

## Вариант 1 — локальная разработка

Frontend в dev-режиме обращается к backend на `http://localhost:8080`, поэтому backend и frontend запускаются отдельно.

### 1. Backend

Из корня репозитория:

```powershell
go run ./cmd/api
```

Backend будет доступен на:

```text
http://localhost:8080
```

### 2. Frontend

Во втором терминале:

```powershell
cd frontend
npm install
npm run dev
```

Vite обычно запускает приложение на:

```text
http://localhost:5173
```

# API

Frontend использует `RecapService` через ConnectRPC.

Основные RPC:

```text
ListProfiles
GenerateRecap
GetRecap
GetPublicShare
```

Proto-контракт:

```text
proto/recap/v1/recap.proto
```

TypeScript-схемы используются frontend-клиентом и преобразуются в локальную доменную модель перед отображением.

# Принципы, которых я придерживался во frontend

### Backend определяет бизнес-решение

Frontend не решает, какое поведение, achievement или next action получил пользователь. Он отображает уже сформированный результат.

### Не придумывать данные

Если данных нет в API-контракте, UI не должен создавать псевдо-факты ради красивого экрана.

### Privacy by design

Личный recap и публичный SHARE — разные представления с разным набором данных.

### Story first

Главная цель интерфейса — провести пользователя через историю, а не показать ему административную таблицу метрик.

### Responsive by default

Компонент считается законченным только тогда, когда он работает не только на большом desktop, но и на узких и низких экранах.

### Декор не должен мешать содержанию

Анимации, звук, haptics и визуальные эффекты используются как enhancement. Они не должны перекрывать текст, ломать layout или становиться необходимыми для навигации.

# Итог моего вклада

Моя часть проекта — это полноценный пользовательский frontend вокруг backend-механики итогов года.

Я занимался не только написанием React-компонентов, но и всей пользовательской стороной решения: **структурой story, визуальным языком, адаптивностью, навигацией, интерактивностью, безопасным SHARE, звуковой обратной связью, accessibility и границей между бизнес-логикой и представлением**.

В результате backend-ответ превращается не в набор JSON-полей или таблицу статистики, а в законченную персональную историю, которую удобно пройти на desktop и мобильном устройстве и которой можно безопасно поделиться.
